# Decisions (ADR-lite)

Append-only. To change a decision, add a new ADR with `Supersedes: ADR-00X` and mark the old one `Status: Superseded`.

Template:
```
## ADR-00X: Title
**Date:** YYYY-MM-DD · **Status:** Proposed | Accepted | Superseded
**Context:** why a decision is needed
**Decision:** what we chose
**Consequences:** trade-offs, follow-ups
```

## ADR-001: Next.js App Router on Vercel
**Date:** 2026-11-04 · **Status:** Accepted
**Context:** Prototype is a Vite SPA. We need server-side auth checks, SEO for public pages, and server code for trusted writes.
**Decision:** Next.js App Router, Server Components by default, Server Actions for mutations, deployed on Vercel Hobby.
**Consequences:** Prototype `App.tsx` must be split into routes/components. Vercel Hobby is for non-commercial use.

## ADR-002: Firebase Spark plan, no Cloud Functions
**Date:** 2026-11-04 · **Status:** Accepted
**Context:** Must stay on free tiers. Cloud Functions require the Blaze plan.
**Decision:** All trusted server logic runs in Next.js on Vercel using `firebase-admin`. Firestore + Firebase Auth only.
**Consequences:** No scheduled jobs; leaderboard periods roll over lazily. Must design for Firestore daily quotas.

## ADR-003: Session cookies + custom claims for roles
**Date:** 2026-11-04 · **Status:** Accepted
**Context:** Four roles; portal routes must be protected server-side and in Firestore rules.
**Decision:** Role stored as Auth custom claim (rules + server checks) and mirrored on `users/{uid}`. httpOnly session cookie via `createSessionCookie`. Middleware does a presence check; layouts verify.
**Consequences:** Role changes require token refresh/revocation.

## ADR-004: Media hosting without Firebase Storage
**Date:** 2026-11-04 · **Status:** Proposed (owner to confirm)
**Context:** Cloud Storage for Firebase requires the Blaze plan for new projects' buckets. Course creators need images (covers, lesson images) and videos.
**Decision (proposed):** Videos as YouTube/Vimeo embeds (privacy-enhanced YouTube). Images via Cloudinary free tier with signed uploads from a server action; until then, creators paste image URLs. Revisit if the project moves to Blaze.
**Consequences:** Adds one external service; no large file uploads in v1.

## ADR-005: Students log in with username + password created by a parent
**Date:** 2026-11-04 · **Status:** Accepted (pending owner confirmation for 13–16 self sign-up)
**Context:** Children 10–16 may not have email; we want parental involvement and minimum data.
**Decision:** Parent creates child accounts; server creates Auth user with synthetic email on `STUDENT_LOGIN_DOMAIN`. Parent can reset the password.
**Consequences:** No email-based recovery for students; parent is the recovery path.

## ADR-006: Server-only gamification with idempotent XP ledger
**Date:** 2026-11-04 · **Status:** Accepted
**Context:** Points must not be forgeable; refreshes must not double-award.
**Decision:** XP, levels, streaks, badges and leaderboards are written only in server transactions. Each award first creates `users/{uid}/xpEvents/{eventKey}`.
**Consequences:** Every award costs a few reads/writes; keep awards per lesson, not per block.

## ADR-007: Child-safe social features
**Date:** 2026-11-04 · **Status:** Accepted
**Context:** Users are minors.
**Decision:** No chat, comments or public profiles. Leaderboards are opt-in by a parent, show nickname + preset avatar only, and display top 10 + own rank.
**Consequences:** Less "social" engagement by design.

## ADR-008: Next.js 16 defaults and tooling versions
**Date:** 2026-11-04 · **Status:** Accepted
**Context:** `create-next-app@latest` now produces Next.js 16.4 with `cacheComponents`, `partialPrefetching` and the React Compiler on by default. These change rendering rules (e.g. `new Date()` during prerender fails the build; `usePathname` may need a `<Suspense>` boundary).
**Decision:** Keep the Next 16 defaults. Use `'use cache'` for time-based values in server components and wrap client components that read URL data in `<Suspense>`. Tooling: Vitest 5 (needs `@types/node` ≥ 22, so we use `^24` to match Node 24), Prettier 3, and `eslint-config-prettier` (one-line justification: turns off ESLint style rules that would conflict with Prettier). Markdown is excluded from Prettier so docs stay as authored. `.gitattributes` forces LF line endings (team works on Windows).
**Consequences:** Agents must read `node_modules/next/dist/docs/` before using Next APIs (see `AGENTS.md`, regenerated by `next dev`). If `cacheComponents` causes too much friction for Firebase data later, revisit with a new ADR.

## ADR-009: Phase 1 dependencies and local Firebase setup
**Date:** 2026-11-04 · **Status:** Accepted
**Context:** Phase 1 adds Firebase Auth, Firestore, session cookies and rules tests.
**Decision:** Runtime: `firebase` (client SDK), `firebase-admin` (server), `zod` (validation), `server-only` (build error if server code reaches the client) — all from the CLAUDE.md stack. Dev: `firebase-tools` (emulators + deploy; pinned in the repo so `npm run emulators` and `npm run test:rules` work without a global install), `@firebase/rules-unit-testing` (official rules test helpers), `tsx` (run TypeScript scripts such as `scripts/set-role.ts`). Local development and tests use the emulators with the `demo-studysathi` project id: the `demo-` prefix means the tools never contact a real Firebase project.
**Consequences:** Java 11+ is needed for the emulators (owner machine has 25). Production project id is added later with `firebase use --add`.

## ADR-010: Sign-up flow, creator applicants, and the signed-in hint cookie
**Date:** 2026-11-04 · **Status:** Accepted (creator-applicant default pending owner confirmation)
**Context:** Phase 1 needs self sign-up for parents and creator applicants, a way into the site from the public header, and role checks that work with Cache Components.
**Decision:**
- Parents get the `parent` role at sign-up. Creator applicants get a user doc with `role: null, requestedRole: 'creator'` and no claim; they see a "what happens next" note at `/account` until an admin approves them (Phase 4 adds the application form and review queue).
- After sign-in the browser goes to `next` (same-site paths only) or the role's home (`/learn`, `/parent`, `/creator`, `/admin`, or `/account` without a role), using a full page load so new cookies apply everywhere.
- The header shows "Log in" / "My account" from a readable, non-secret `ss_signed_in` cookie, read in the browser. Reading the real session in the header would make every public page dynamic (a server invocation per view); the hint keeps them static. All real checks use the httpOnly session cookie on the server.
- Session cookie lasts 7 days; sign-out revokes refresh tokens on every device.
- No email copy in `users/{uid}`; Firebase Auth holds it.
**Consequences:** A stale hint cookie (expired session) shows "My account", which leads to the login page. Fine. Promoting a creator later means `assignRole(..., 'creator')`, which also clears `requestedRole`.

## ADR-011: Admin data access layer and catalogue caching
**Date:** 2026-11-05 · **Status:** Accepted
**Context:** Next renders layouts and pages in parallel, so a role check in a portal layout does not stop the page's data fetching or keep its output out of the RSC payload. Separately, public pages must not cost Firestore reads per visitor.
**Decision:** Admin reads go through functions in `src/lib/admin/*` that each call `requireAdmin()`. Server Actions re-check with `getAdmin()` and return typed results. The public catalogue is one cached server read (`getCatalog`, tag `catalog`) refreshed by `updateTag` after admin edits, with a short-lived seed fallback. Deleting a resource that a learning path uses is blocked. Admins cannot change their own role or turn off their own account. Rules tests use project id `demo-studysathi-rules` (emulator `singleProjectMode: false`) so they never wipe dev data.
**Consequences:** New portal pages must call a guarded data function or `requireRole()` themselves; a layout gate alone is not enough.

## ADR-012: Learner progress is server-trusted and per-course
**Date:** 2026-11-05 · **Status:** Accepted
**Context:** The learner flow needs a real course path: enroll, go to the first lesson, complete a lesson, and continue. These actions cannot rely on client-only storage because a user could bypass or replay them.
**Decision:** Enrollments live in `courseEnrollments/{uid_courseId}` and lessons are tracked in `courseProgress/{uid_courseId}` with a `completedLessons` array. The server writes these values from authenticated student actions only; the UI reads them as a server-view snapshot. The first lesson is selected from the course outline and used as the canonical route forward after enrollment.
**Consequences:** We need a lightweight lesson route and a completion action, but we avoid client-side trust issues and keep progression easy to audit later for XP and analytics.

## 2026-11-05 ? Course compatibility and review boundary
Keep the established inline outline model for current courses: outline is { modules: [...] }, with one kind per lesson. Read older array-shaped outlines without rewriting live data. Save canonical objects. Stacked block documents, sort and budget remain explicit unfinished work. Creator writes are transactional and draft-only; publishing remains admin-only. Plain text is escaped, never rendered as raw HTML. Quiz feedback is practice; it awards no mastery score or XP.

## 2026-11-05 ? Private library and view counts
Store bookmarks, path progress and private notes together at users/{uid}/privateData/library for one read per navigation and low read cost. This supersedes the originally planned per-note/per-bookmark storage for the current library. All reads/writes validate the student session on the server; default-deny client rules remain. Merge is idempotent, keeps account notes on conflicts and only clears guest state after confirmed success. Apply per-document bounds and debounce notes.
Course views mean once per authenticated session-cookie lifetime per course. Store only a SHA-256 session/course digest in courseViews, never the raw cookie. The event and counter increment are atomic. expiresAt supports future cleanup; no TTL policy was deployed. Enrollment and completion counters start from tracked events; no historical backfill was performed. No new dependencies were added.

## 2026-11-05 - Optional stacked activities in inline lessons
Preserve current course outline reads and stable lesson IDs. Add an optional blocks array (1-12 validated content blocks) to each lesson; old lessons continue rendering their existing content. A stack replaces the parent display content and is completed once at lesson level. Each activity has a unique ID and independent practice state. Keep inline storage for the modest LMS and reject serialized outlines above 700 KB; splitting into lesson documents is deferred rather than forcing a live migration. Sort/budget are existing planned types; both provide practice feedback without awarding client-controlled XP. Budget activities use fictional NPR whole rupees, 2-6 categories and a bounded total. No new dependency.

## 2026-11-05 - Lesson reward rollout
Start rewards prospectively: existing completed lessons stay complete and do not gain replay XP. New lessons earn fixed 10 XP, first lesson of a Kathmandu day +5, and the first completing lesson of a course +50. Progress, hashed xpEvents and user stats commit atomically, including concurrent tabs. No client chooses award amounts. Quiz practice remains ungraded and gives no points/perfect badge until a trusted quiz-grade action exists. Apply seeded badge definitions locally for bounded reads; do not silently map Digital Safety to the broader digital-skills category. Levels follow the documented thresholds through 1000 XP and add 350 XP per level afterward. Static reward feedback supports reduced motion without confetti. Weekly totals use Sunday-start Kathmandu dates for future leaderboards, which remain opt-in and unimplemented. No dependency added.

## 2026-11-05 - Trusted quiz rewards and consented leaderboards
First pass means first successful server-graded submission, even after practice retries. The current quiz has one single-choice question, so a correct submission is a perfect quiz. Grant +5 XP once per user/course/lesson/quiz ID using a hashed quiz ledger key; do not change lesson streak/count or award daily/course bonuses on a quiz event. Both legacy single-format and stacked quiz blocks are graded from the current published course and require enrollment. Creator preview gives no points.
Leaderboards store only XP at leaderboards/{all-time|Kathmandu-Sunday-date}/entries/{uid}; no names or private text are duplicated. Only a linked parent can consent. Opt-in includes existing all-time and current-week totals; opt-out deletes both current entries in the same transaction as the flag. Awards update entries only when that transaction reads consent=true, preventing reappearance after concurrent withdrawal. Admin disable/role change also withdraw consent; re-enabling an account does not silently re-consent. Current names/avatars and consent are checked on each guarded server read, with only presentation fields returned. Archived week entries contain IDs/XP only and are not exposed by the current-period UI. Queries use existing automatic single-field XP indexes; no index/rules deployment needed for the server-only implementation.
Digital Safety is now an explicit course category (digital-safety), distinct from digital-skills; Safe Explorer matches that canonical category. Existing courses are not recategorized and live badge documents are not rewritten; runtime reward rules use the seeded code definitions. No new dependency.

## 2026-11-05 - Bounded aggregate analytics and comparable cohorts
Creator analytics never query learner identities, notes or individual progress. Read owned course stats only; lists select title/status/stats and paginate 20 documents. Aggregate each counter independently so sparse legacy documents cannot exclude unrelated sums. Creator workspace needs only three status counts. Admin metrics use a separately guarded global aggregate.
Keep recorded totals prospective and label limits. Add analyticsVersion=1 to new enrollments plus stats.analyticsEnrollments and stats.analyticsCompletions in the existing enrollment/completion transactions. The displayed completion rate uses only this comparable new-enrollment cohort; older enrollment documents are not relabeled or backfilled. Increment stats.lessonCompletions by literal FieldPath only for a first lesson completion. Bars show relative recorded completions in outline order; skipped or unfinished lessons are not proof of abandonment, so no false dropout claim is shown. No index definitions or deployed indexes were changed; production query/index acceptance is still pending. No dependency added.

Analytics reference: [Firestore aggregation behavior](https://firebase.google.com/docs/firestore/query-data/aggregation-queries). Independent sums avoid the documented intersection of documents containing every field in a multi-field aggregation.

## 2026-11-05 - Course metadata readiness and compatibility
Drafts may omit cover/description/language, but review submission and publishing require an HTTPS cover URL, a 2-240 character image description, an explicitly selected content language and valid course details/lessons. Supported content languages are English, Nepali, and English and Nepali; this does not add translated UI. Missing legacy language is not inferred as English. Existing published courses remain readable without a metadata migration; republishing requires the new checklist.
Use externally hosted image URLs and next/image unoptimized so arbitrary creator URLs are not fetched through a server image proxy. The cover handles load failure and never renders unsafe URL schemes. Shared fields/checklist keep new/edit/review views consistent. Metadata and outline save atomically and only while draft; forced status=draft and schema stripping prevent injected status/ownership. Admin publication now reads/validates/writes in a transaction, preventing a stale validation race with creator edits. No dependency added; no live courses or environment settings changed.
